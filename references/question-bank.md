# 问答模板库

> 读取时机：Phase 0 问答环节。目标是系统性地消除用户需求中的灰度区域。

---

## 通用 7 问（必问）

### Q1. 做什么？

**问题**：这个 skill 要帮 agent 完成什么任务？用一句话描述。

**判断标准**：
- ✅ 好的回答：有明确动词 + 明确对象，如"根据中文描述生成建表SQL"
- ❌ 差的回答：太模糊，如"处理数据库"、"帮忙写代码"

**追问提示**（如果用户回答模糊）：
- "能具体说说，输入是什么、输出是什么吗？"
- "如果 agent 用了这个 skill，用户最直接能看到的结果是什么？"

---

### Q2. 什么时候用？

**问题**：用户说什么话或在什么场景下应该触发这个 skill？

**判断标准**：
- 至少有 2-3 个触发词
- 触发词要考虑中英文、口语/书面语
- 包含"即使没明确提到 skill 名也应该触发"的场景

**追问提示**：
- "用户可能会怎么描述这个需求？用他们自己的话。"
- "有没有用户不会直接说'我要用这个skill'，但实际需要它的情况？"

**anti-under-trigger 原则**：
description 应"略带攻击性"——宁可多触发也不要漏触发。例如：
- ❌ "生成建表SQL"
- ✅ "根据中文描述生成建表SQL。当用户提到建表、创建数据库表、根据描述生成表结构、设计表、数据库设计时使用，即使用户没有明确说'建表'。"

---

### Q3. 什么时候不用？

**问题**：哪些场景看起来相关但不应该触发这个 skill？

**常见 NOT 场景**：
- 只查询数据（不建表）→ 不触发建表 skill
- 只读代码（不做 review）→ 不触发 code-review skill
- 只是简单操作（不值得用 skill）→ 不触发复杂流程 skill

**追问提示**：
- "有没有和这个 skill 功能相近但不应该触发的场景？"
- "另一个 skill 可能更适合处理什么情况？"

---

### Q4. 输入是什么？

**问题**：skill 执行时需要接收什么输入？

**输入类型速查**：

| 类型 | 示例 | 处理方式 |
|------|------|---------|
| 文件路径 | `/path/to/file.sql` | 先检查文件存在 |
| 文本内容 | 中文描述、SQL 语句 | 直接使用 |
| URL | Wiki 链接、API 端点 | 先获取内容 |
| 用户选择 | 从列表中选择 | 提供选项 |
| 环境变量 | 数据库配置 | 前置检查 |

**追问提示**：
- "输入是必需的还是可选的？"
- "如果用户没提供某个输入，怎么获取或处理？"

---

### Q5. 输出是什么？

**问题**：skill 执行后产生什么输出？

**输出类型速查**：

| 类型 | 示例 | 注意事项 |
|------|------|---------|
| 文件 | `.sql`, `.md`, `.json` | 指定路径和命名规则 |
| 代码 | SQL、Go、PHP | 指定格式规范 |
| 报告 | Markdown 文档 | 指定章节结构 |
| 终端输出 | 命令结果 | 指定展示格式 |
| 状态变更 | 数据库更新 | 需确认机制 |

**追问提示**：
- "输出是给用户看的还是给其他系统用的？"
- "对输出格式有特定要求吗？（比如 JSON 格式、特定的 Markdown 结构）"

---

### Q6. 有什么约束/规则？

**问题**：执行过程中必须遵守的规则或边界？

**约束分类**：

| 类别 | 示例 |
|------|------|
| 格式约束 | "所有时间字段用 int 类型时间戳" |
| 安全约束 | "禁止生成 DROP/DELETE 无 WHERE" |
| 业务约束 | "默认 InnoDB 引擎"、"必须包含 id/ctime/utime" |
| 性能约束 | "单次处理不超过 1000 行" |
| 兼容约束 | "兼容 MySQL 5.7+" |
| 🔴 公开发布安全约束 | 见下方安全红线速查 |

**安全红线速查**（公开发布时强制）：

细则（S001-S004 规则表、环境变量方案、脱敏规则）以 SKILL.md Step 1.3 为唯一权威来源，此处仅作追问入口。

**追问提示**：
- "有没有绝对不能违反的规则？"
- "如果违反了规则怎么处理？自动修正还是报错？"
- "skill 是否需要连接外部服务（数据库/SSH/API）？如果是，连接信息如何管理？"
- "skill 是否涉及敏感数据（手机号/地址等）？输出时是否需要脱敏？"

---

### Q7. 依赖什么？

**问题**：需要什么工具、环境、其他 skill？

**自动探测**：
```bash
# 检查常用工具
which gh python jq curl rg docker node npm
```

**依赖分类**：

| 类型 | 示例 | 缺失处理 |
|------|------|---------|
| CLI 工具 | `gh`, `jq`, `python3` | 提示安装 |
| MCP 服务 | 企业 Wiki、Issue 跟踪 | 标记为可选 |
| 其他 Skill | sql-gen | 引用说明 |
| 运行环境 | Node.js 18+ | 前置检查 |
| 环境配置 | `.env` 文件（数据库/SSH/API 地址） | 前置检查 + `.env.example` |
| 网络访问 | SSH 隧道、VPN | 前置检查 + 连接说明 |

**追问提示**：
- "没有这个依赖能运行吗？有什么替代方案？"
- "这个依赖是必须的还是可选的？"
- "需要连接外部服务吗？连接信息是否已有配置文件管理？"

## 证据项补齐（新增）

> 读取时机：Q1-Q7 完成后、进入 Phase 1 之前。用于避免“拍脑袋生成”。

### E1. 用户真实样例输入（至少 2 条）

- 目的：验证触发词与真实语境是否一致，避免只覆盖“理想输入”。
- 要求：两条输入至少有一条是口语化表达。

### E2. 目标输出验收样例（至少 1 条）

- 目的：明确“什么算完成”，避免生成结果不可验收。
- 要求：给出最小可用输出样例（可是 Markdown/JSON/SQL 之一）。

### E3. 必守约束来源（至少 1 条）

- 目的：约束有出处，避免规则来自主观猜测。
- 来源优先级：项目规范 > 历史案例 > 用户口头约束。

### 需求置信度打分

| 等级 | 判定条件 | 处理动作 |
|------|----------|----------|
| 高 | E1/E2/E3 全部齐全且约束来源清晰 | 可进入 Phase 1 生成 |
| 中 | 缺 1 项，或约束来源不完整 | 先补齐缺口，再生成 |
| 低 | 缺 2 项及以上 | 禁止直接生成，必须先追问 |

### 标准确认输出模板（可直接复用）

```markdown
## 需求证据确认

### E1 用户真实样例输入（>=2）
1. {样例输入1}
2. {样例输入2}

### E2 目标输出验收样例（>=1）
- {验收样例1}

### E3 必守约束来源（>=1）
- 来源：{规范/文档/历史案例}
- 约束：{约束描述}

### 置信度结论
- 置信度：{高/中/低}
- 依据：{命中项与缺失项}
- 下一步：{直接进入 Phase 1 / 先补齐缺失证据}
```

使用要求：
- 在进入 Phase 1 前，必须先输出该模板并让用户确认。
- 置信度为“低”时，不可跳过补证据步骤。

### Phase 0 输出契约

进入 Phase 1 前的输出项与结构化模板，以 SKILL.md「Phase 0 输出模板」为唯一权威来源（入口模式/需求规格/证据结论/置信度/下一步 5 项）。

## 模式专属追问

### P1 工具调用模式追问

- **Q1a**：工具的命令是什么？有哪些参数？
- **Q2a**：有没有常见的参数组合或最佳实践？
- **Q3a**：工具返回结果是什么格式？需要后处理吗？
- **Q4a**：工具常见错误有哪些？怎么处理？

### P2 路由分发模式追问

- **Q1b**：分支条件有哪些？如何判断走哪个分支？
- **Q2b**：各分支的处理逻辑差异在哪？
- **Q3b**：有没有"默认分支"？无法匹配时怎么处理？
- **Q4b**：分支间是否有共享的逻辑（可提取为公共步骤）？

### P3 流程编排模式追问

- **Q1c**：步骤间的依赖关系是什么？哪些步骤必须等前一步完成？
- **Q2c**：哪些步骤可以并行执行？
- **Q3c**：检查点的通过/失败标准是什么？
- **Q4c**：某步失败时，是重试、跳过还是中止？

### P4 状态机模式追问

- **Q1d**：有哪些状态？状态间的转换条件？
- **Q2d**：什么情况下需要回退？回退到哪个状态？
- **Q3d**：有没有"终态"？到达终态后做什么？
- **Q4d**：状态转换有无副作用？（如发送通知、修改数据）

### P5 护栏模式追问

- **Q1e**：有哪些必须遵守的规则？优先级如何排序？
- **Q2e**：规则校验是自动的还是需要人工确认？
- **Q3e**：违规时如何处理？自动修正还是报错？
- **Q4e**：有没有"零容忍"规则（违反即中止）？

## 问答技巧

### 当用户说"不知道"

**策略**：给出该问题的常见选项，让用户选择。

**示例**：
- 用户："我不知道有什么约束"
- Agent："这类任务常见的约束有：1) 格式约束（如字段命名规范）2) 安全约束（如禁止危险操作）3) 业务约束（如必须包含特定字段）。有适用的吗？"

### 当用户回答矛盾

**策略**：指出矛盾，请用户澄清。

**示例**：
- 用户说"自动处理"又说"必须人工确认"
- Agent："您提到要'自动处理'，又说'必须人工确认'，这两个似乎矛盾。是指：A) 先自动处理，关键步骤人工确认？还是 B) 全部人工确认？"

### 当用户需求太宽泛

**策略**：缩小范围，先做核心场景。

**示例**：
- 用户："我想做一个处理所有数据库操作的skill"
- Agent："这个范围太大了，建议先聚焦一个核心场景。比如：1) 建表 2) 数据迁移 3) 查询优化。先做哪个？"

### 当用户需求太窄

**策略**：适度泛化，提高 skill 复用性。

**示例**：
- 用户："帮我写一个处理 users 表的 skill"
- Agent："这个需求可能太具体了。是否可以泛化为'根据任意表描述生成建表SQL'？这样 users 表只是其中一个用例。"
