# 多阶段协议契约（Protocol Spec）

> 读取时机：进入 `skill-creator` 工作流前。  
> 目的：把“会写 skill”变成“可验证交付”。

## 总体约束

- Phase 0-6 必须按顺序执行，除非触发降级路径。
- 每个 Phase 必须有可见产物，否则视为未完成。
- 低置信度（证据缺 2 项及以上）禁止进入 Phase 1。
- 每次优化只允许改一个维度，确保可归因。
- 无法实测时必须显式标记 `eval_mode: dry_run`。

## 阶段输入输出

| Phase | 输入 | 输出 | 失败回退 |
| --- | --- | --- | --- |
| 0 意图与需求 | 用户原始诉求 | 入口模式 + 需求规格 + 证据结论 | 缺证据回到问答补齐 |
| 1 模式与骨架 | 需求规格 | 模式判定 + SKILL 草稿 | 模式冲突回到 Phase 0.4 |
| 2 评测设计与执行 | SKILL 草稿 | test-prompts + 评分结果 | 用例缺类回到 2.1 |
| 3 迭代优化 | 评分短板 | 单点优化结果 + 重评 | 两轮无收益提议结构重组 |
| 4 验证交付 | 优化后版本 | 脚本校验 + 手检 + 交付摘要 | 验证失败回到 3 |
| 5 后置精炼 | 已通过交付包 | 双评审改进清单 | 无可归因改动则跳过 |
| 6 跨 Skill 一致性 | 交付包 + 协议基线 | 联动一致性报告 | 不一致回到 2 或 4 |

## 入口分流契约

入口模式（CREATE/EXTRACT/IMPROVE/DIAGNOSE）的判定标准与执行差异以 SKILL.md Step 0.1 的模式表为唯一权威来源，本文件不再重复维护。

## 证据契约（Phase 0.5）

E1/E2/E3 的构成、接受标准与置信度打分唯一权威：[question-bank.md](question-bank.md)「证据项补齐」与「需求置信度打分」；置信度对 Phase 推进的门禁判定（高/中/低各自去向）以 SKILL.md Step 0.5 为唯一权威。本文件不重复维护。

## 检查点模板

Checkpoint 1.5（模式与骨架）与 Checkpoint 2.5（评测解释）的输出模板以 SKILL.md（Step 1.5 / Step 2.5）为唯一权威来源，本文件不重复维护，避免双处漂移。

## 交付契约（Phase 4）

交付摘要必须严格包含以下字段，输出模板以 SKILL.md「交付清单」为唯一权威来源：

- `Skill` / `模式` / `验证` / `评测`

## dry_run 契约

触发条件：
- 子 agent 不可用
- 关键依赖缺失且无法安装
- 运行环境受限

执行要求：
- 明确标记 `eval_mode: dry_run`
- 给出路径可达性评分依据
- 明确说明未覆盖的真实执行风险

## 附录：端到端示例（简版）

用户输入：

```text
帮我做一个 skill：根据中文业务描述生成 MySQL 建表 SQL，必须包含 id/ctime/utime，禁止 DROP。
```

各阶段产出的字段与结构以 SKILL.md 对应模板为唯一权威（Phase 0 输出 / Checkpoint 1.5 / Checkpoint 2.5 / 交付摘要），此处不复制，避免双处漂移。
