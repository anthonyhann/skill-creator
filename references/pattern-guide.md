# Skill 设计模式指南

> 读取时机：Phase 1 选择模式前。选错模式是最常见的 skill 编写错误。

---

## 五种设计模式

### P1. 工具调用模式（Tool Call）

**核心思想**：封装一个工具/SDK 的调用流程，让 agent 不需要知道底层细节就能稳定完成输入→转换→输出。

**适用场景**：
- 单一工具或 SDK 的封装
- 线性步骤，无分支
- 输入→转换→输出的明确管道

**识别信号**：
- 用户说"调用 XXX 接口/工具/命令"
- 任务是"把 A 格式转成 B 格式"
- 步骤是固定的、线性的

**SKILL.md 结构**：

```markdown
# {Skill 名称}

## 前置条件
- {依赖的工具/环境}

## 执行步骤
1. {步骤1：输入验证/预处理}
2. {步骤2：核心转换/调用}
3. {步骤3：输出格式化/后处理}

## 输出格式
{输出模板/示例}

## 异常处理
| 场景 | 处理 |
|------|------|
| {输入缺失} | {提示用户提供} |
| {工具不可用} | {fallback 方案} |
```

**反模式**：
- ❌ 在 skill 里写复杂条件分支 → 应该用 P2
- ❌ 步骤超过 7 步 → 拆分子 skill 或用 P3

**示例**：mysql-table-creator（中文描述 → 建表 SQL 生成器）
- 输入：中文自然语言描述
- 转换：生成建表 SQL
- 输出：格式化的 SQL 语句

---

### P2. 路由分发模式（Router）

**核心思想**：根据输入类型/条件，将请求分发到不同的处理逻辑，各分支独立处理。

**适用场景**：
- 多种输入类型需要不同处理
- if/else 选择逻辑
- 按语言/框架/平台分发

**识别信号**：
- 用户说"根据 XX 类型分别处理"
- 任务有明确的分类标准
- 不同类型间的处理逻辑差异大

**SKILL.md 结构**：

```markdown
# {Skill 名称}

## 路由规则

| 条件 | 分支 | 说明 |
|------|------|------|
| {条件1} | {分支A} | {说明} |
| {条件2} | {分支B} | {说明} |
| {条件3} | {分支C} | {说明} |

## 分支 A：{名称}
{处理逻辑}

## 分支 B：{名称}
{处理逻辑}

## 输出格式
{统一输出模板}

## 异常处理
| 场景 | 处理 |
|------|------|
| {无法匹配分支} | {默认分支/报错} |
```

**反模式**：
- ❌ 分支间处理逻辑高度相似 → 合并为一个分支，用参数区分
- ❌ 分支超过 5 个 → 考虑拆分为多个 skill
- ❌ 分支条件模糊 → 条件必须可判定

**示例**：code-review（按语言分发规则集）
- 按代码语言路由：Golang → golang 规则集，PHP → php 规则集，Vue → vue 规则集
- 各分支规则独立，但输出格式统一

### P3. 流程编排模式（Orchestrator）

**核心思想**：多步骤有序执行，步骤间有数据传递，关键节点有检查点确保质量。

**适用场景**：
- 复杂多步骤工作流
- 步骤间有数据依赖
- 需要检查点/质量门

**识别信号**：
- 用户说"先做A，再做B，最后做C"
- 步骤间有明确的先后依赖
- 某步骤的输出是下步骤的输入

**SKILL.md 结构**：

```markdown
# {Skill 名称}

## 前置条件
- {依赖列表}

## Step 1：{名称}
- 输入：{本步骤接收什么}
- 操作：{做什么}
- 输出：{产生什么}
- 检查点：{通过标准}

## Step 2：{名称}
- 输入：{来自 Step 1 的输出}
- 操作：{做什么}
- 输出：{产生什么}
- 检查点：{通过标准}

## ...

## 输出格式
{最终输出模板}

## 异常处理
| 步骤 | 失败场景 | 处理 |
|------|---------|------|
| Step N | {场景} | {重试/回退/报错} |
```

**反模式**：
- ❌ 没有检查点 → 步骤可能静默失败
- ❌ 检查点标准模糊（"看起来对"）→ 必须用可判定的标准
- ❌ 步骤可并行却串行 → 标注哪些步骤可并行执行

**示例**：order-e2e-tester（端到端下单链路演练）
- Step 1：准备测试数据
- Step 2：创建订单
- Step 3：查询订单状态与价格
- Step 4：提交订单
- Step 5：模拟状态回调
- 每步有明确的输入/输出和检查点

### P4. 状态机模式（State Machine）

**核心思想**：定义明确的状态和转换规则，支持回退/重试，确保任务在正确的路径上推进。

**适用场景**：
- 有明确状态流转的任务
- 需要回退/重试逻辑
- 状态间有条件转换

**识别信号**：
- 用户说"如果A失败了就回退到B"
- 任务有明显的阶段/状态
- 需要根据条件跳转或回退

**SKILL.md 结构**：

```markdown
# {Skill 名称}

## 状态定义

| 状态 | 描述 | 可转换到 |
|------|------|---------|
| {状态A} | {描述} | {状态B, 状态C} |
| {状态B} | {描述} | {状态D, 状态A} |

## 转换规则

| 当前状态 | 条件 | 目标状态 | 动作 |
|---------|------|---------|------|
| {状态A} | {条件1} | {状态B} | {执行XX} |
| {状态A} | {条件2} | {状态C} | {执行YY} |

## 各状态行为

### {状态A}
{在这个状态下做什么}

### {状态B}
{在这个状态下做什么}

## 回退规则
| 场景 | 回退到 | 原因 |
|------|--------|------|
| {XX失败} | {状态A} | {说明} |

## 输出格式
{最终输出模板}
```

**反模式**：
- ❌ 状态超过 8 个 → 拆分为多个 skill
- ❌ 回退规则缺失 → 每个失败路径都必须有明确的回退
- ❌ 状态定义模糊 → 状态名应能直接判断当前处于哪个阶段

**示例**：api-tester-debug（接口排障状态机）
- 状态：SSH连接 → 日志查询 → 数据库查询 → 根因分析
- 根据日志/数据库结果决定是否需要进一步查询
- 可回退到前一步重试

### P5. 护栏模式（Guardrail）

**核心思想**：用规则集严格约束输出，在生成后校验，确保合规/安全/格式正确。

**适用场景**：
- 需要严格输出格式控制
- 安全/合规约束
- 输出必须通过校验才能交付

**识别信号**：
- 用户说"输出必须是 XX 格式"
- 需要安全检查（SQL 注入、XSS 等）
- 输出有明确的校验规则

**SKILL.md 结构**：

```markdown
# {Skill 名称}

## 规则集

| ID | 规则 | 校验方式 | 优先级 |
|----|------|---------|--------|
| R1 | {规则描述} | {自动/手动} | P0 |
| R2 | {规则描述} | {自动/手动} | P1 |

## 执行步骤
1. {生成/处理步骤}
2. {校验步骤}
3. {修正步骤（如需）}

## 输出校验清单
- [ ] {校验项1}
- [ ] {校验项2}

## 违规处理
| 规则 | 违规处理 |
|------|---------|
| R1 | {自动修正/报错/回退} |
```

**反模式**：
- ❌ 规则集太大（>15 条）→ 拆分为 P0/P1/P2 优先级
- ❌ 校验清单没有可判定的标准 → 每条必须是 ✓/✗ 可判定
- ❌ 违规只报错不修复 → 提供 auto-fix 路径

**示例**：sql-gen（SQL 生成 + 安全校验）
- 生成 SQL 后自动校验：SQL 语法、安全规则（无 DROP/DELETE 无 WHERE）、结果自检
- 违规时自动修正或报错

## 模式组合

当任务同时满足多个模式的特征时，可以组合使用：

| 组合 | 适用 | 示例 |
|------|------|------|
| P2 + P1 | 先路由再调用 | 按语言分发 → 各调用不同工具 |
| P3 + P5 | 流程编排 + 护栏 | 多步骤流程，最终输出需校验 |
| P3 + P2 | 流程中某步有分支 | 主流程线性，某步内按条件分发 |
| P4 + P5 | 状态机 + 输出校验 | 状态流转，每次状态转换校验输出 |

**组合原则**：
1. 主模式只有一个，辅助模式嵌套在特定步骤中
2. 组合不超过 2 种（3 种以上说明 skill 太复杂，应拆分）
3. 在 SKILL.md 中明确标注主模式和辅助模式
4. 选型完成后必须输出 Checkpoint 1.5 摘要（模板见 SKILL.md Step 1.5，唯一权威来源）

## 决策树（详细版）

```
Q1. 任务是否涉及多个互斥分支（按类型/语言/框架分发）？
    YES → P2（路由分发）
    NO  → Q2

Q2. 任务是否有明确的状态定义和转换规则？
    YES → Q2a
    NO  → Q3

    Q2a. 状态间是否有回退/重试需求？
        YES → P4（状态机）
        NO  → P3（流程编排，状态退化为步骤）

Q3. 任务是否有3个以上有序步骤且步骤间有数据依赖？
    YES → P3（流程编排）
    NO  → Q4

Q4. 任务是否需要严格约束输出格式/内容/安全？
    YES → P5（护栏模式）
    NO  → P1（工具调用）

--- 组合判定 ---

Q5.（在选定主模式后）是否需要额外模式？
    - P1 主模式 + 输出需校验 → P1 + P5
    - P2 主模式 + 分支后有多步骤 → P2 + P3
    - P3 主模式 + 某步骤按条件分发 → P3 + P2
    - P3 主模式 + 输出需校验 → P3 + P5
```

## 反模式汇总

### "万能 Skill"

一个 skill 试图做所有事。5 种模式特征都有 → 说明应该拆成多个 skill。

**信号**：SKILL.md 超过 800 行，5+ 个 ## 二级标题互不相关。

**修复**：按职责拆分，用 references/ 引用共享部分。

### "路由无默认"

P2 模式但路由规则无法覆盖所有输入。未匹配的输入被忽略或报错。

**修复**：路由规则必须有"其他"默认分支。

### "流程无检查点"

P3 模式但步骤间没有检查点。某步静默失败，后续步骤在脏数据上运行。

**修复**：每个步骤后加检查点，检查点标准必须可判定。

### "状态爆炸"

P4 模式但状态数超过 8 个。状态转换图变得不可读。

**修复**：合并相近状态，或拆分为多个 skill。

### "护栏太松"

P5 模式但规则集只有 2-3 条泛泛的约束。输出质量没有实质保障。

**修复**：规则集至少 5 条，每条有明确的校验方式和违规处理。
